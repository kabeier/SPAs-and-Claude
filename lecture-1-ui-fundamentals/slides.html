A user interface is everything a user can see, touch, click, type into, or get feedback from

  • Buttons, menus, icons
  • Forms, text fields, sliders
  • Images and text
  • Navigation
  • Feedback: errors, toasts, spinners

It's a bridge

Computers speak code and data. People speak buttons. When you click Send on an email, you never write the networking code. The UI hides it behind one button.

Quick test: "Is a loading spinner part of the UI?" Yes, it's feedback. "Is the database?" No.

Students' earlier stateful-components activity connects here: every slider, toggle, and input you found is a UI element.

"World-class chefs, great recipes. But if the menu is confusing and nobody takes your order, you leave. You never taste the food." The UI is the only part users experience directly.

Then land why it matters: users judge the whole app by the UI. First impressions take seconds, and if they can't find a feature it doesn't exist. Your backend work is invisible without it.

Our running example is the curriculum's Workout Tracker.

Identify your application

What is it? One or two sentences.

"A lightweight, mobile-first workout tracker that lets users quickly log exercises, sets, reps, and weight during a workout, and view their history over time."

What problem does it solve?

  • Why would someone use it?
  • What's frustrating about the current process?
  • How do people solve it today?

Workout Tracker

Problem: "I log workouts in spreadsheets and notebooks. It's messy and I can't really track my progress."

Today: notebook, Notes app, memory

Push for specific problems. "People need to work out" is not a problem. "Mid-set, with sweaty hands, I can't type into a spreadsheet" is.

Who are the users?

  • Who will use it?
  • Is there more than one type of user?
  • What is each one responsible for?
  • What does each one need to see?

Different users, different interfaces

A food delivery app has 3 UIs:

  • Customer: browse and order
  • Driver: pickups and map
  • Restaurant: incoming orders

Workout Tracker: one user, the lifter.

Quick chat question: "Netflix (your homework): how many user types?" Viewers, plus profiles (kids vs adult). Plant that seed for homework.

Clarify features: users don't care about your code, they care about finishing tasks

User goals

  • What are they trying to accomplish?
  • Top 3 reasons they open the app?
  • What do they do most often?
  • Which actions create value?

Workout Tracker, top 3

  1. Log a set fast, mid-workout
  2. See what I lifted last time
  3. See that I'm getting stronger

This is where beginners skip ahead to colors and buttons. The top 3 decides what goes on the home screen.

Information and actions: think CRUD

C

Create

Log a new workout or set

R

Read

View history and records

U

Update

Fix a typo in a set

D

Delete

Remove a set or workout

Also: search · filter · sort · export · share

And: what should users never see? (other people's data, passwords, admin tools)

Every major action usually becomes a feature, and usually a button.

CRUD shows up again in the backend unit, so keep it light: "Create, Read, Update, Delete. Almost every app is these four verbs on some kind of data."

Optional 30-sec check: "Instagram: liking a post is which one?" (Create a like / Update). "Scrolling your feed?" (Read).

Write the user journey: the step-by-step story of using your app

What happens when a user…

  • first visits?
  • signs up / logs in?
  • completes their main task?
  • makes a mistake?
  1. Opens app → sees last workout
  2. Taps Start Workout
  3. Picks exercise, logs sets
  4. Types "abc" for reps → red hint under the field, nothing else cleared
  5. Taps Finish → lands on History

Point out step 4: the mistake is part of the journey. Callback to the crime scene.

Now draw it: screens in TLDraw

List your screens

Home · Dashboard · Profile · Settings · Search results · Details · Reports · Admin

For each screen

  • What information appears?
  • What actions, buttons, forms?
  • What navigation?

TLDraw in 30 seconds

  • R rectangle · A arrow · T text · N sticky note
  • Ctrl/⌘ D duplicate a screen
  • Drag an arrow from one screen to another for navigation
  • Boxes and labels only. No colors, no fonts.
  • Save the .tldr file and export PNGs. You'll need them next lecture.

Do a 20-second live demo in tldraw.com if you have time: draw a phone frame, two boxes, an arrow.

What should happen when something goes wrong?

  • Login fails
  • Internet disconnects
  • Form validation fails
  • Payment fails
  • User enters invalid data
  • The list is empty

The most-skipped step

Beginners only design the happy path. Real users mostly live on the unhappy paths.

Write the error state onto the wireframe itself: what it says and what the user can do next.
